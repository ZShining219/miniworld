# MiniWorld 前端呈现硬性规则

> 状态：Accepted，所有后续前端任务必须遵守
>
> 生效日期：2026-09-03
>
> 适用范围：`apps/miniworld-shell/**`、`frontend/**` 以及任何新增的用户界面

## 1. 权威性与执行方式

本文件把用户确认的前端呈现要求固化为工程门禁。它从属于用户最新明确指令、根目录 `goal.md` 和隐私/审批边界，但高于页面局部实现便利、模板默认样式和历史自定义 CSS。

以下词语具有强制含义：

- **必须**：不满足时不得声称完成、验收通过、推送或部署；
- **禁止**：不得在新代码中出现，历史代码在被实质修改时必须同步收敛；
- **允许**：可采用，但不能降低本文件其他验收门；
- **例外**：只有技术上无法遵守且用户明确确认后才成立，必须在 `goal/decisions.md` 和 `goal/implementation-log.md` 记录原因、影响、替代措施和回滚方式。

每个前端任务开始前必须：

1. 阅读本文件；
2. 在治理任务的 `expected_output` 中列出适用的呈现验收项；
3. 声明修改的是手机端、PC 端或两者；
4. 明确将使用的成熟组件及确实需要自定义的业务组件；
5. 列出必须覆盖的页面状态与目标视口。

## 2. 前端分层与技术基线

### 2.1 手机端

- 手机 H5、未来 App 和微信小程序继续使用 `unibest + uni-app + Vue 3 + TypeScript`，不得为了视觉修复重写业务层或另建未经决策的新运行时。
- 通用呈现组件必须采用 unibest 官方推荐的 **Wot UI 2.x**，包名为 `@wot-ui/ui`；正式接入时必须固定版本、记录许可证并通过 H5 构建，App/小程序只有实际构建验证后才能声称兼容。
- 在 Wot UI 2 接入完成前，禁止继续新增通用按钮、输入框、选择器、弹层、提示、空状态、导航栏、列表容器或表单布局。相关任务必须先完成组件库接入。
- Fitness 等业务可保留“训练组记录、动作切换、训练状态”等领域组件，但其基础控件、反馈和布局必须由组件库与设计令牌组成。

### 2.2 PC 端

- PC 工作台继续使用现有 `React + TypeScript + Vite`，不得仅为统一视觉迁移业务路由或构建系统。
- 通用控件默认采用 **Ant Design**；复杂表格、查询表单和详情页允许按需使用 **Ant Design ProComponents**。
- 当前阶段禁止仅为了呈现引入完整 Ant Design Pro/Umi 重构；只有 PC 工作台确实发展为复杂中后台且用户明确确认后才允许评估。
- MapLibre、ECharts、Tauri 窗口控制等专用组件可以保留，但外围导航、表单、反馈、空态和操作区必须遵守同一套组件与令牌规则。

### 2.3 两端关系

- 手机端和 PC 端必须共享 API schema、业务状态名称、权限含义、错误语义和颜色语义。
- 禁止为了“复用 UI 代码”强行让手机端与 PC 端共用 Vue/React 组件或同一页面布局。
- 手机端优先单手操作、短路径和低信息密度；PC 端优先可扫描性、批量查看和键鼠效率。

## 3. 组件库优先规则

新增或修改界面时，必须按以下顺序选择实现：

1. 选定组件库的现成组件；
2. 由现成组件组合出的项目级模式；
3. 由现成基础控件构成的业务组件；
4. 只有前三项无法满足业务语义时才允许自定义基础呈现。

禁止：

- 在业务页面直接使用裸 `button`、`input`、`select`、`textarea` 模拟通用控件；
- 为已有组件库能力另写按钮、输入框、弹窗、Toast、加载态、空状态或表单校验样式；
- 用多个近似组件分别解决同一种交互；
- 在页面 scoped CSS 中创建新的全局颜色、字号、间距、阴影或圆角；
- 复制粘贴整段公共 SCSS 到多个页面；
- 通过绝对定位、固定像素偏移或隐藏溢出来掩盖布局问题；
- 因为自动化测试能通过，就绕过组件库的可访问性与移动端处理。

历史自定义组件不是永久豁免。页面或组件被实质修改时，受影响的通用控件必须一并迁移到选定组件体系；若本轮无法完成，必须登记 `pending_review`，不得把新增债务标为完成。

## 4. 设计令牌

颜色、字体、间距、尺寸、圆角、边框、阴影和层级必须来自一个项目级主题入口；页面只能引用语义令牌，禁止写散落的魔法值。

最低要求：

- 颜色必须使用 `primary`、`success`、`warning`、`danger`、`text-primary`、`text-secondary`、`surface`、`border` 等语义名称；
- 字体只允许使用预定义层级：辅助、正文、强调正文、小标题、页面标题、数据强调；
- 正文在手机端不得小于 `14 CSS px`，可编辑输入不得小于 `16 CSS px`；
- 手机端交互热区不得小于 `44 × 44 CSS px`；
- 间距使用 4 的倍数形成的有限序列，不得为单页创造任意间距；
- 同类按钮、输入框和卡片必须使用统一高度、圆角与边框；
- 不得仅靠颜色表达状态，必须同时有文字、图标或结构提示；
- 系统字体为默认字体，除非用户明确要求，不得用装饰字体承担正文或主要操作。

uni-app 的 `rpx` 只允许用于经主题统一映射的布局尺寸。禁止在业务页面用独立 `rpx` 数值自由定义字号。H5 根样式必须明确设置 `text-size-adjust: 100%` 和 `-webkit-text-size-adjust: 100%`，并保留可访问的系统字体缩放能力。

## 5. 页面模板

每个页面必须归属以下一种模板；若都不适用，必须先扩展本文件再实现：

1. **列表页**：导航/标题、可选筛选、列表、空态、加载/失败态、主要新增入口；
2. **详情页**：导航、对象摘要、分组信息、次级操作、独立危险操作区；
3. **表单页**：标题、字段组、就地校验、固定或明确的提交区、离开保护；
4. **任务页**：当前状态、主要任务内容、单一下一步、暂停/结束等次级操作；
5. **统计页**：范围选择、摘要指标、可视化、空数据解释、明细入口；
6. **设置页**：分组设置、修改反馈、危险配置隔离、历史数据影响说明。

手机页面的标准顺序必须是：

`系统/应用导航 → 必要状态摘要 → 当前任务内容 → 单一主要操作 → 次级信息/危险操作`

禁止：

- 页面标题、状态卡、正文和按钮重复表达同一信息；
- 把编辑表单常驻在主要任务流中；新增/编辑应使用独立页面、Sheet、Dialog 或明确展开区；
- 为追求“极简”留下没有信息作用的大面积空白；
- 让危险操作成为页面最醒目的默认主按钮；
- 同一视口同时出现两个互相竞争的主要操作。

## 6. 状态与业务一致性

每个用户可见页面必须实现并验证以下适用状态：

- 初始加载；
- 正常数据；
- 空数据；
- 部分数据；
- 请求失败；
- 提交中；
- 提交成功；
- 提交失败与安全重试；
- 无权限或策略阻断；
- 离线或后端不可用。

状态呈现必须对应真实业务规则，禁止只处理视觉结果。Fitness 额外必须满足：

- 空计划不得开始训练；开始按钮必须禁用或替换为“先添加动作”；
- 已有进行中训练时，同一计划不得再次显示“开始训练”；
- 进行中训练与历史完成状态不能同时作为主状态；
- 无动作的进行中 Session 必须提供清晰恢复路径，不能只剩“结束训练”；
- “结束训练”、归档、删除等危险操作必须与主要操作分区并二次确认；
- 添加动作不得与记录训练组争夺首屏主要操作；
- 正式训练记录只来自 PostgreSQL，呈现层不得以本地草稿冒充已保存结果。

## 7. 手机端响应式与输入规则

- 布局必须从手机端开始设计，再扩展到宽屏；禁止把 PC 页面缩窄后当作手机页面。
- 必须覆盖至少 `320、360、390、430 CSS px` 四档宽度；断点不得只针对某一台设备。
- 任何手机表单默认单列。只有两个短数值字段可以并列，操作按钮必须独占一行或放入固定操作区；禁止三列“字段 + 字段 + 按钮”。
- 必须支持顶部安全区、底部安全区、浏览器地址栏/工具栏伸缩和虚拟键盘出现后的可滚动区域。
- 输入必须声明正确键盘类型、单位、范围和格式；数字输入必须能在真实手机上完成编辑、清除、恢复和错误提示。
- 文本必须允许合理换行；重要按钮文字不得截断；禁止以缩小到不可读字号解决空间不足。
- 横向滚动只能用于时间轴、标签带或明确的横向浏览组件，普通页面不得横向溢出。
- 固定底部操作不得遮挡内容，内容区必须包含相应安全间距。

## 8. PC 端布局规则

- PC 页面必须在 `1280 × 720` 和 `1440 × 900` 验证；关键内容不得依赖超宽屏。
- 主导航、页面标题、筛选、内容、批量操作和详情必须有稳定层级。
- 表格必须处理加载、空态、错误、长文本、窄列、分页和横向滚动；禁止靠截断隐藏关键业务信息。
- 表单必须使用统一 label 对齐、字段宽度、校验和提交反馈。
- 破坏性操作必须降权并要求确认；外部写入继续遵守 `goal.md` 的显式审批边界。
- PC 响应式不等于手机适配；PC 页面在窄屏只需安全降级，不得宣称替代手机端。

## 9. 可访问性与文案

- 所有可操作元素必须有可识别名称和键盘/触控状态；图标按钮必须有 `aria-label` 或对应跨端属性。
- 焦点态、禁用态、加载态和错误态必须可见。
- 正文、次要文字和控件必须满足 WCAG AA 对比度；不得用低对比灰色隐藏重要信息。
- 文案优先使用用户任务语言，禁止无信息价值的英文装饰标题；保留英文时必须有明确产品意义。
- 状态文案必须回答“发生了什么、现在能做什么”；错误不得只显示技术异常。
- 数字必须带单位或明确上下文，时间、重量、次数和距离不得依赖用户猜测。

## 10. 验收门

### 10.1 自动化

所有前端行为变更必须通过：

- TypeScript 类型检查；
- 变更范围 ESLint/Biome；
- 相关单元和组件测试；
- 对应生产构建；
- 关键页面状态的 Playwright 流程；
- 稳定关键页面的截图基线或等价视觉回归比较；
- 浏览器控制台无新增 error/warning；
- 无非预期横向溢出。

截图基线至少覆盖：正常数据、空数据、错误态和一个主要操作过程。视觉差异必须人工审阅，不得仅依赖像素阈值自动放行。

### 10.2 真实设备

以下变更部署生产前必须有真实手机验收：

- 页面结构、导航、表单或主要操作变化；
- 字体、间距、固定定位、安全区或响应式变化；
- 键盘输入、长按、拖动、手势、Canvas 或图表变化；
- 组件库、主题、构建入口或 viewport 变化。

真实手机验收至少记录：

- 设备/系统和浏览器；
- 页面截图；
- 默认字体和较大系统字体；
- 浏览器底栏可见及收起后的结果；
- 虚拟键盘打开后的输入与提交；
- 主要操作、返回、失败恢复与危险确认；
- 是否出现遮挡、跳动、溢出、误触或不可读内容。

桌面浏览器设置 `360 × 800` 或 `390 × 844` 只能算预检，**不能替代真实手机验收**。“无横向溢出”“测试通过”或“页面能打开”均不能单独证明视觉验收通过。

### 10.3 完成定义

只有同时满足以下条件才能标记前端任务完成：

- 使用了指定组件体系，或有已批准例外；
- 页面属于明确模板；
- 所有适用状态均有实现和证据；
- 自动化验收全部通过；
- 需要真实设备的变更已完成真实设备验收；
- 截图经人工确认达到可交付质量；
- 实现日志记录命令、结果、视口、设备和已知延期；
- 不违反隐私、模块隔离与外部写入审批边界。

未满足真实设备或人工视觉审阅时，只能记录为“本地实现完成，等待视觉验收”，禁止写“移动端已验证”“生产验收完成”或同义表述。

## 11. 变更策略

- 下一次手机端呈现工作必须先接入 Wot UI 2 和主题令牌，再改造业务页面；禁止继续在现有手写 SCSS 上逐页打补丁。
- Fitness 页面应按“壳与状态 → 表单与反馈 → 列表与空态 → 训练任务 → 统计”顺序迁移，每个批次可独立回滚。
- PC 端在下一次通用页面改动前接入 Ant Design；已有专用地图和 Agent 可视化无需为了统一而重写。
- 组件迁移不得改变 API、数据库、隐私或审批语义；视觉重构与业务功能新增原则上拆分为不同提交。
- 引入第三方库必须固定版本、保留许可证、验证产物体积和目标平台，并通过现有 secret/PII 扫描。
